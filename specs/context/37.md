## Relevant details

### What was requested

> **Note on the shipped design vs. the issue's original framing.** The issue framed
> the QA work as a 7-phase pipeline with **Phases 5–7 sequential** ("review reads
> the code first, then QA plans and drives the running product"). During
> implementation this pivoted: the pipeline stays 5 phases, and `/plan-qa` +
> `/execute-qa` ship as an **independent, unnumbered QA gate** that the developer
> runs in parallel with or alongside `/review` at their discretion. The
> `acceptance-coverage` policy also pivoted: the issue promised a `run-tests.sh`
> invoker and a Runtime Evidence Protocol; the shipped review check ships
> **static-only** instead, reading assertion bodies and never running the suite.
> Both pivots are deliberate (see commit `a7b19bc` "neutral QA framing" for the
> QA-gate shape; the static-only policy is codified in
> `dev-pipeline/skills/review/sub-skills/requirement-coverage.md` and
> `task-completion.md`).

1. A `sync-skills` skill that mirrors this repo's skills into another harness's
   skills directory (via `scripts/sync-skills.sh` + `scripts/sync-targets.json`),
   accepting natural-language requests like "copy the skills to oh-my-pi".
2. A QA gate that runs **independently of Phase 5** (`/review`):
   - `/plan-qa` — turns specs + diff into an executable QA spec (cases with
     `[bash]`/`[browser]` tagged steps, `Guard:`-codified traps, Coverage Map
     over every changed file, `[assert]` / `[judge]` Expected lines).
   - `/execute-qa` — runs the spec as written, writes verdicts to a separate
     `QA-RESULTS-*.md` file (never modifies the plan), one appended section per run.
