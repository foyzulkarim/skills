# Task 35: feat: generalize worktree/archive/release skills into dev-pipeline plugin

- **Type:** feat
- **Source:** GitHub issue #35
- **State:** OPEN
- **Labels:** none
- **Created:** 2026-07-24

## Description

## Summary
Four skills currently living only as claude-lens-specific copies in `~/.claude/skills/`
(`archive-issue`, `finish-worktree`, `move-to-worktree`, `release-notes`) should be
generalized and added to the `dev-pipeline` plugin's supporting skills, so any project
can install them via `/install-plugin` and get correct, non-claude-lens-specific behavior.

`create-issue` is explicitly out of scope for now.

## Why
These were copied from claude-lens's project-local `.claude/skills/` into the user-level
directory, but they hardcode claude-lens paths (`specs/claude-lens-plan.md`,
`specs/wiki-structure.md`), the project name, and a bespoke worktree port formula
(`4128 + 10 * issue#`). They'll misbehave or be irrelevant in any other repo as-is.

dev-pipeline already has its own generic artifact conventions (`specs/context/<id>.md`,
`specs/requirements/REQ-<slug>.md`, `specs/architecture/ARCH-<slug>.md`, `specs/reviews/`,
`{type}/{number}/{slug}` branch naming — see `start-task`). Generalizing these skills is
mostly a matter of aligning them to those conventions instead of claude-lens's bespoke ones.

## Scope (draft — to be refined via /plan-requirements or /plan-architecture)

- **finish-worktree** — script is already fully generic; only the SKILL.md's
  post-teardown reminder references `specs/claude-lens-plan.md` and needs generalizing.
- **move-to-worktree** — replace the hardcoded port formula/env var with an optional,
  config-driven mechanism (skip gracefully if not configured); replace hardcoded `npm ci`
  with package-manager detection (npm/pnpm/yarn), skipping install if none is found.
- **release-notes** — drop "for claude-lens" wording; generalize version-source detection
  beyond `package.json` (Cargo.toml, pyproject.toml, VERSION file, git tags).
- **archive-issue** — the biggest change. Drop the dependency on a per-project
  `wiki-structure.md` and `claude-lens-plan.md` phase structure; inline the correlation
  model into the skill itself. Add a wiki-readiness check (clone + bootstrap
  `Home.md`/`_Sidebar.md` skeleton if missing). Group the wiki index flatly by issue
  number instead of by plan phases. Resolve the issue anchor directly from
  `gh issue view` instead of a `specs/issues/` record (since `create-issue` is out of scope).

## Out of scope
- `create-issue` skill.
- Any changes to the `claude-lens` repo (it keeps its own bespoke local copies).

## Next steps
Run through the dev-pipeline properly: `/plan-architecture` (or `/plan-requirements` first
if scope needs more interrogation) → `/generate-tasks` → `/implement` → `/review`.
